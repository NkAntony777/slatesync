## 结论

SlateSync 的 LTC 解码已经越过了大多数商用工具的公开承诺线，不该在这条线上继续加码。真正值得投入的是另一端——**把"分轨正确对齐并打包"升级为"成品听起来像在同一个房间里录的"**，以及**让产出物满足交付合规**。

差距集中在三处，且都可以在现有架构上做，不需要引入依赖、不破坏单文件版形态：

1. **补齐空白用的是数字静音（digital silence），不是房间声（room tone）。** 这是行业里最刺耳的一条。当一条轨晚开机或提前停录，工具补的是绝对零电平，而人耳会把绝对静音读成"掉轨"而不是"安静"（FlashBoards, *Room Tone*）。专业对白编辑的做法是拿现场的房间声去填，且要与两侧做谱匹配和交叉淡化。
2. **边界是硬切，没有交叉淡化。** `src/wave-combine.js:516` 的越界分支直接调用 `writeSilenceSample` 写零，与真实音频之间没有任何过渡。这在波形上是一个阶跃必然产生咔哒声。
3. **交付物在响度与真峰值上完全不合规。** `bext` 写的是 version 1（`src/wave-combine.js:185`），不含 EBU Tech 3285 version 2 规定的五个响度字段；输出 chunk 只有 `bext` / `iXML` / `fmt` / `fact` / `data`，没有 `axml`，没有 `chna`。整个 `src/` 里没有出现 LUFS、Loudness、dither、true-peak 中的任何一个。

这三条对应一次真实的升级：**P0-1 房间声填充、P0-2 等功率交叉淡化、P0-3 EBU R128 响度与真峰值**。

## 市面上的成熟做法是什么

行业里"把散轨变成成品"的完整链路，专业做法大致是六步：先对齐（sample-accurate）、再择优（段落级 comping）、再匹配视角与混响（perspective / ambience）、再做谱平衡（spectral balance）、再填缝与过渡（room tone + crossfade）、最后按目标响度归一化并做合规检查。Pro Tools 的 ADR 课程把这条链路写得很直白——"Edit ADR for sync, perspective, ambience, spectral balance, and dynamics"，其中 ambience 与 spectral balance 是和 sync 同级的必做项，而不是可选项（https://infinitecreation.io/course-pro-tools-adr ）。

其中对 SlateSync 最有参考价值的三类外部成果：

**房间声（room tone）是独立素材，不是副产品。** 它在现场就要专门录：通常 30–60 秒、无人说话无人走动、麦位与对白轨一致、空调灯光状态与拍摄时相同。后期用它去填咳嗽、场记板、说错词造成的洞，用来在不同 take 之间做过渡底子，用来垫在 ADR 底下让干声"坐进"场景。行业还普遍用它当降噪算法的学习样本（noise print），而不是从对白间隙里抠——那些间隙短、脏、带呼吸和衣料声，循环起来能听出来（https://flashboards.yaroflasher.com/learn/sound/room-tone ）。

**交叉淡化用等功率，不用等增益。** 等增益的线性淡入淡出在中点总增益是 0 dB，但人耳的响度感知是对数的，于是中点会出现一个可闻的功率凹陷；对白轨这尤其致命，因为它等于凭空开了一个"洞"。等功率曲线（−3 dB 交点）让感知响度在整个过渡里保持恒定，是行业对白的默认选择。另外，编辑点本身要落在零交叉或低能量处，而不是在一段持续音的中间（https://audioscene.org/techniques-for-creating-smooth-audio-crossfades-in-dialogue-editing ）。

**房间声之外，还要做谱匹配。** 单独一条对白轨和垫在下面的房间声，在频谱上不是一回事；不做匹配，混合后底噪会显出"另一个空间"的颜色。RX 系列的 Spectral De-noise 会持续学习背景底噪特征，Dialogue Isolate 则用神经网络做来源分离；RX 12（2026 年 4 月）进一步加了 Scene Rebalance，把场景拆成对白、音乐、音效三条 stem 分轨处理（https://www.edgechat.ai/izotope ）。这类工具提供的是"分离"，而 SlateSync 需要的是更克制的"匹配"——只做低电平底噪区间的平滑频谱补偿，不要动对白主导的高频。

**相位对齐是独立的一层，不是极性取反。** 领夹与吊杆之间的距离差会造成 2–3 ms 的到达时间差，合成到单声道母线时形成梳状滤波，把人声掏空成鼻音。专业做法是在采样级对齐并对齐相位，动态场景则依赖连续相位跟踪工具（如 Sound Radix Auto-Align Post 2、MeldaProduction MAutoAlign）；这类工具的存在本身说明静态对齐不够——演员走动时麦位距离在变（https://infinitecreation.io/tutorial-dialogue-editing-cleaning-lav-boom-phase ）。

**交付合规是一条独立的规范线，不是"响度听起来差不多"。** EBU R 128 给出 −23 LUFS 的节目响度目标与真峰值上限，具体测量按 ITU-R BS.1770 的 K 加权与双段门控实现（EBU Tech 3341 细化）；Netflix 近场是对白门控的 −27 LKFS，Apple 播客约 −16 LKFS。关键在于这些数字彼此不可换算——门控方式不同，差值就不是四个 LU 而是两个不同的测量。所以合规工具的正确形态是"按目的地选目标并写入测量结果"，而不是"一键统一响度"（https://www.versely.studio/blog/loudness-targets-by-destination-not-one-number ）。

**AAF 是最终交接格式，但不该由本工具实现。** Final Cut Pro X 没有原生 AAF 导出，行业路径是 FCPXML → X2Pro（付费，Marquis Broadcast）或 FCPXML → DaVinci Resolve → AAF（免费）两条（https://www.forte-ai.com/blog/how-to-create-a-pro-tools-friendly-aaf-from-final-cut-pro-x ）。对浏览器工具来说，提供 FCPXML 1.9 sidecar 比自研 AAF 写入器现实得多。

国内语境下还有一条现实约束：GY/T 364—2023《4K 超高清晰度电视节目录制规范》对音频录制、视音频同步、节目文件封装都有要求，其中明确使用 dB FS 与 dB TP 两个单位，并给出环绕声节目声道分配表（https://gdj.shaanxi.gov.cn/xwzx/bmdt/tzgg/202303/P020240809377908827970.pdf ）。响度与真峰值这一层，早晚会从"加分项"变成"接单前提"。

## 升级建议

### P0-1　房间声填充，取代数字静音

把 `planFromMeasurement` 产出的 `headPadSamples` / `tailPadSamples` 从"静音长度"改成"待填充长度"，填充内容由新模块 `src/room-tone.js` 提供。

算法分四步。第一步提取噪声指纹：在 take 内按短时 RMS 排序，取最安静的一段（默认 2 秒），计算其平均功率谱作为该场景的底噪模板 `S_tone(f)`。若用户另外指定了一条 room tone 轨，优先用那条——现场专门录的底噪质量远高于对白间隙里抠出来的碎片。

第二步生成填充素材。优先直接复用 take 内部的静音片段（自补），取两段不连续的静音、中间用等功率交叉淡化拼接，避免单一素材循环产生的可辨重复感。静音素材不足时，降级为按 `S_tone(f)` 重合成噪声：随机相位 + 慢速幅度起伏，使底噪听起来是活的而不是一层平稳的纸。

第三步做谱匹配。计算填充段与两侧真实内容段在低电平主导区间的谱差，拟合一条平滑增益曲线（1/3 倍频程粒度）补偿给填充段。**只作用于底噪主导的频段**，对白主导的高频不动——过度处理会暴露"这是一段合成噪声"。

第四步处理接缝，与 P0-2 共用同一条等功率交叉淡化逻辑。

这里必须守住 SlateSync 既有的一条底线：**测不出来就返回 null，绝不猜。** 没有可用静音段、也没有指定 room tone 轨时，如实报告"无法自动填充，建议手工补录房间声"，而不是拿噪声糊上去。这和 LTC 的零误锁红线是同一条原则的两次体现。

### P0-2　等功率交叉淡化

在 `src/wave-combine.js` 的取样层引入"边界窗口"概念。当一条轨从越界区（补白区）进入真实内容、或从真实内容进入越界区时，在一段窗口内做等功率过渡，而不是一步跨过去。

边界位置是可以精确算出来的——它就是偏移量与漂移比共同决定的 `leadSamples` / `driftRatio` 落点，不存在估计误差。过渡长度建议默认 20 ms（48 kHz 下 960 采样），可配。

还有一处行业细节值得实现：编辑点应该落在零交叉或低能量处。工具可以在边界附近 ±5 ms 的窗口内搜索能量最低的位置，把过渡放在那里。人工做这一步很花时间，自动化之后效果立竿见影。

曲线选择等功率（sin/cos 互补），不是等增益（线性互补）——理由是等增益在对白中点会造成可闻的功率凹陷，恰好在需要无缝的地方挖了个洞。

### P0-3　EBU R128 响度与真峰值合规

分两部分：**测量**与**写入**。

测量部分实现 ITU-R BS.1770-4：K 加权（48 kHz 下两级双二阶——高频架 + 高通）、400 ms 瞬时窗、3 s 短时窗、带绝对门限与相对门限的双段门控积分，以及 LRA。全部可以在现有 `src/ltc-feedforward.js` 的 FIR 基础设施上扩展，不需要新依赖。

写入部分把 `bext` 升到 version 2，填入 EBU Tech 3285 规定的五个字段（整数格式，单位 ×100）：

| 字段 | 偏移 | 类型 | 含义 |
|---|---|---|---|
| `LoudnessValue` | 412 | i16 | 积分响度 LUFS×100 |
| `LoudnessRange` | 414 | u16 | 响度范围 LU×100 |
| `MaxTruePeakLevel` | 416 | i16 | 最大真峰值 dBTP×100 |
| `MaxMomentaryLoudness` | 418 | i16 | 最大瞬时响度 LUFS×100 |
| `MaxShortTermLoudness` | 420 | i16 | 最大短时响度 LUFS×100 |

现有的 `bextChunkDataForCombine` 已经分配了 858 字节（602 固定区 + 256 字节 CodingHistory），version 2 的响度字段落在 412–421，**无需扩容**。

同时补一个 `axml` chunk 写入对应的 `LoudnessValue` / `MaxTruePeakLevel` / `MaxMomentaryLoudness` / `MaxShortTermLoudness` / `LoudnessRange` 字段——老工作流读 axml，新工作流读 bext v2，两边都覆盖到。

目标选择做成**按目的地选目标**，不做全局一键归一：EBU R 128 节目 −23 LUFS、ATSC A/85 −24 LKFS、Netflix 近场 −27 LKFS（对白门控）、自定义。每项都必须记录自己用的是哪种测量与门控，因为门控不同数字不可互换。

真峰值用 4× 过采样峰值表。是否附带限制器要谨慎：自动限幅会改变节目动态，专业交付里通常由混音师决定。工具侧建议默认**只测量并报告**，限幅做成显式可选项，并默认天花板设在 −2 dBTP（比 R 128 制作建议的 −1 dBTP 更保守）。

**这一项的验证口径最干净**：可以用 `ffmpeg -af ebur128` 或 `loudnorm` 交叉验证同一文件的积分响度与真峰值，误差应在 0.1 LU 以内。这是全篇最容易被第三方复核的一条，建议作为 P0 验收的基准项。

### P1-1　保留亚采样对齐精度

`measureOffset` 用抛物线插值给出了亚采样精度的偏移量（`src/take-repair.js:77`），但 `planFromMeasurement` 里的 `lead = -Math.round(offsetSamples)`（`src/take-repair.js:187`）把它取整了；同时 `writeCombinedData` 只在 `repair.driftRatio !== 1` 时才做线性插值（`src/wave-combine.js:528`）。

结果是：**两台设备时钟一致、只存在纯偏移的常见场景下，亚采样精度被完整丢弃。** 这条路径恰好覆盖了"同机多轨对齐"和"两台同型号录音机对齐"这类最普遍的用法。

保留它不需要大改：让 `plan` 携带浮点偏移，把取样公式改成 `(outputFrame - leadFractional) / driftRatio`，插值条件改为"存在小数部分"而非"存在漂移"。对单声道对白，0.5 采样的差异（48 kHz 下 10 µs）听不出来；但对**需要把两支麦克风叠到同一母线**的场景，采样级误差会直接变成梳状滤波。是否做连续相位对齐（lav 与 boom 差 2–3 ms ≈ 100–150 采样）是更大的题，动态相位跟踪是专业插件的领域，本工具不必追；但至少不该在有能力的时候把精度丢掉。

### P1-2　谱匹配（与 P0-1 配套）

P0-1 第三步的频谱补偿需要一套独立的实现：长时平均频谱（LTAS）差异提取 + 平滑增益曲线拟合 + 渐变应用。增益曲线建议限制在 ±3 dB 以内、1/3 倍频程粒度平滑，并在交叉淡化窗口内渐变进出，避免突变。

### P2-1　chna chunk

Poly WAV 的全部价值在于"第 N 通道就是第 N 支麦克风"，但目前这个信息只存在于 iXML 的 track list 里。`chna`（EBU Tech 3285 配套的通道分配 chunk）是它的现代等价物，Resolve、Pro Tools、以及所有按 BW64 读 ADM 的工具都会认。写起来不复杂：通道索引 + 一个短标签，可直接从现有的 `sourceTrackKey` 与 `trackNameForSource` 取。

这一步是通往沉浸式交付（BW64 + ADM，ITU-R BS.2088 / BS.2076 / BS.2127）的第一步——ADM 的引用完整性检查里，`fmt` 的声道数与 `chna` 表对不上是致命错误。建议先把 `chna` 做对，沉浸式作为后续路线单独评估。

### P2-2　抖动

目前输出固定 PCM24，不涉及降位深。一旦支持 16-bit 输出，TPDF 抖动是必需项而非可选项——不抖动的 24→16 截断会在安静段落产生可闻的量化台阶。加上抖动只需在量化前注入 TPDF 噪声，代价极小。

### P3-1　FCPXML sidecar

不自己写 AAF 写入器。改为输出一份 FCPXML 1.9 sidecar，让 Resolve 导入后导出 AAF（或由后期用 X2Pro 转换）。这比自研 AAF 便宜两个数量级，且落在 Resolve 已实测通过的能力范围内。

## 建议不要做的

**不要引入机器学习降噪或来源分离。** RX 的 Dialogue Isolate、Scene Rebalance 效果很好，但它们依赖权重模型、不可复现、拖不动单文件版，也违背 SlateSync 的本地优先与可审计原则。SlateSync 的差异化在"每一步结果可解释、可复核、宁可不做也不错做"，ML 降噪恰好抹掉这个属性。谱匹配（P1-2）能做到跨接自然，这已经覆盖了绝大部分痛点。

**不要继续在 LTC 解码上加码。** 现有链路的零误锁表现已经优于商用工具的公开承诺，而误锁在时码写回场景里是 P0 级事故。覆盖率提升与误锁风险之间永远是负相关的，这笔账不划算。

**不要在真实素材验证之前打开任何默认开启。** P0-1 与 P0-2 会改变音频内容，必须与现有"对齐修复"一样**默认关闭**、显式勾选才生效。仓库里已经确立的"关闭时输出与改动前逐字节相同"这条承诺，同样适用于这两项。

**不要把"多 take 段落级择优"顺手做进来。** SlateSync 目前的模型是"一个 take 的多支分轨 → 交付 Poly"，而跨 take 的择优拼接（行业里的 clip comping）需要段落级切分、逐段打分、候选比较，是另一个量级的功能。如果真实需求里"合板"包含择优拼接，这需要单独立项，不该混在本次升级里。

## 落地顺序

| 序 | 升级项 | 收益 | 代价 | 验收口径 |
|---|---|---|---|---|
| 1 | P0-2 等功率交叉淡化 | 消除咔哒声 | 小（取样层局部改动） | 边界波形无阶跃；与现有关闭路径逐字节一致 |
| 2 | P0-3 R128 响度与真峰值 | 交付合规 | 中（K 加权 + 双二阶 + bext v2 + axml） | 与 `ffmpeg ebur128` 交叉验证误差 < 0.1 LU |
| 3 | P0-1 房间声填充 | 合板成品"像真的" | 中大（噪声指纹 + 合成 + 谱匹配） | 盲听测试：填充段与邻接段不可区分 |
| 4 | P1-1 亚采样精度保留 | 同场景更准 | 小 | 已知偏移注入测试，误差 < 0.1 采样 |
| 5 | P2-1 chna chunk | 通道语义可被工具读取 | 小 | Resolve 导入后通道标签正确 |
| 6 | P1-2 / P2-2 / P3-1 | 补齐配套 | 小到中 | 各自独立验收 |

前三项建议作为一个版本交付，因为它们共同构成"成品可听 + 成品合规"这条完整链路；单做其中之一，用户拿到手的仍是不完整的工作流。
