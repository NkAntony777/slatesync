# 合板全能体：三条腿与一条流水线

> 这份文档回答一个问题：要把 SlateSync 做成"专业合板全能体"，工程上该怎么搭。
> 不是功能愿望清单，是**结构**：哪几块共用、哪几块各做各的、边界画在哪。

## 定位

市面上"合板"相关的产品分三类，SlateSync 要做的是**三类里各取一段，做成一条流水线**：

| 腿 | 解决什么 | 代表产品 | SlateSync 的位置 |
|---|---|---|---|
| **A 同步** | 这段声音在哪儿（时间对齐） | PluralEyes、Syncaila、Sidus TC Sync | 从"只认 LTC"扩到"也认波形" |
| **B 编辑** | 选哪一条、怎么拼 | Resolve、Pro Tools、ADR 工具 | **明确不做**（见下） |
| **C 交付** | 写成什么样、够不够格 | EBU 工具、WaveChecker、Sound Devices | 元数据已齐，**缺"读回自检"** |

### B 腿为什么不做

段落级择优（comping）、ADR 录音与对唇，是剪辑与录音棚的活。上游做这些，会把编辑决策提前到合板阶段，与 SlateSync 的位置冲突：SlateSync 的产出是**进剪辑室的素材**，不是成片。真要做 B 腿，正确形态是**导出一个剪辑决策文件**（把择优结果交给 NLE 执行），而不是自己动手。

## 一条流水线，三种测量源

关键认识：**三条腿共享同一条流水线，区别只在"偏移量从哪来"。**

```
        测量层                     对齐层                    交付层            验收层
  ┌──────────────────┐      ┌──────────────────┐      ┌──────────────┐   ┌──────────────┐
  │ LTC 硬同步        │      │                  │      │ BWF v2       │   │              │
  │  时码 → 偏移      │─────▶│ planFromMeasurement│────▶│ iXML / chna  │──▶│ 读回写出的   │
  │  置信度：天然最高  │      │                  │      │ axml / FCPXML│   │ 文件逐条核验 │
  ├──────────────────┤      │ 补白 / 丢 pre-roll│      │ 房间声补白   │   │              │
  │ 波形同步          │      │ 线性重采样 / 极性 │      │ 等功率交叉淡化 │   │              │
  │  包络互相关        │─────▶│                  │      │ 确定性抖动    │   │              │
  │  置信度：突出度+一致│      │ 房间声 / 交叉淡化  │      │              │   │              │
  ├──────────────────┤      │                  │      │              │   │              │
  │ 人工指定          │─────▶│                  │      │              │   │              │
  │  置信度：用户负责  │      └──────────────────┘      └──────────────┘   └──────────────┘
  └──────────────────┘
```

**三种测量产出同一种形状**：`{ offsetSamples, ratio, polarity, confidence }`。

于是：

- `planFromMeasurement`（`src/take-repair.js`）吃它 → 出补白/重采样/极性计划；
- `planFromWaveformMatch`（`src/waveform-sync.js`）吃它 → 出**完全同形**的计划；
- 下游的补白、房间声、交叉淡化、写入，两条路径**一行都不用改**。

这是"集大成"能成立的工程前提：不是把三个功能并排放，而是让它们共用同一套骨架。

## 置信度模型：三条腿共用一套话术

仓库一贯的原则是**"测不出来就返回 null，绝不猜"**（LTC 的零误锁红线）。扩展到三条腿后，这个原则要落成可比较的量：

| 测量源 | 置信度由什么决定 | 不达标时 |
|---|---|---|
| LTC | 硬同步，天然最高；但解出 0 帧的 LTC 仍不可信 | 解码失败 → 不写时码 |
| 波形 | 段一致率（多段是否指向同一位）+ 峰值突出度（内容是否在别处也出现过）+ 片段能量 | 任一不达标 → `analyzeWaveform` 返回 `reason` |
| 人工 | 用户负责 | 无 |

波形路径的诊断接口 `analyzeWaveform` 返回 `{ measurement, confidence, reason }`，
`reason` ∈ `no-signal / too-short / no-quiet-segment / no-observation / low-agreement / low-prominence`。
**界面与日志必须把 reason 说出来**——用户看到"没同步上"没用，看到"内容不相关"才有用。

## 波形同步为什么用包络，不用原始波形

ISO 与摄影机原始声是同一现场的不同麦克风：麦位不同、频响不同，摄影机侧还过了 AGC/降噪/压缩。
原始波形的互相关没有共同结构可比，算出来的峰多半是频谱差异的产物。

**被两路共同保留下来的信息是能量包络**：谁在什么时候说话、有没有动作、什么时候安静下来。
包络去均值后形状一致，互相关才有意义。

实测精度（`test/waveform-sync.test.mjs`）：

| 场景 | 精度 |
|---|---|
| 无麦克风差异 | 采样级（< 8 采样） |
| 另一支麦 + 底噪 | 一帧之内（25 fps 下 20 ms） |

残余误差来自**另一支麦的低通群延迟**——包络法补偿不了物理上的时延。
一帧之内对视频同步够用（时间线的时间栅格本来就是帧）。

## 两条必须说清的边界

- **波形同步给的是"某一刻"的偏移。** 录音机与摄影机的晶振不同，长时间会漂。
  波形同步解决"起点对不上"，持续漂移仍然要靠 LTC（两端都有时码）来管。
  两腿不是互斥的，是互补的。
- **波形同步的输入是摄影机原始声**，那是一路**带压缩、带降噪、可能有 AGC** 的信号。
  这与 ISO 对 ISO（两条干净的轨）不是一回事，判据要分开。

| **QC** | 逐 take 的体检（23 条）、14 项验收清单、**跨 take 的生产级总账**（`_生产总账.json` / `.csv`） | 总账接进交付单模板 / CI |

### 交付自检要核什么（都有现成数据）

- bext v2 的响度字段 **与重新测量的结果一致**（防回填出错）；
- chna 的通道数与顺序 **与 `_channels.json` 一致**；
- 时长 / 采样率 / 位深 **与基准轨一致**；
- 真峰值 **≤ 交付目标上限**；
- 抖动策略与位深一致（32→24 抖了、16→24 没抖）；
- BWF 结构能被第三方解析器读懂。

实际落地的 9 条检查项（`src/delivery-check.js`，顺序固定）：

| 检查项 | 核什么 |
|---|---|
| `bwf-structure` | RIFF/RF64/BW64 容器与 bext 的基本结构能读懂 |
| `loudness-matches` | bext v2 的响度字段与写入时的测量值一致（防回填出错） |
| `true-peak-ceiling` | 真峰值 ≤ 交付目标上限 |
| `axml-present` | axml 里的 `ebu_loudness_information` 在（老工具要读这个） |
| `chna-matches` | chna 的通道数与顺序与 `_channels.json` 一致 |
| `channel-count` | 通道数与计划一致 |
| `sample-rate-bit-depth` | 采样率与位深与基准轨一致 |
| `duration` | 时长与基准轨一致（按 data 段声明长度算帧数） |
| `dither-policy` | 位深下降时确实抖了；升位或同位深时确实没抖 |

判定有三种：`pass`（通过）、`fail`（不通过）、`manual`（工具给不出结论，要人工去看）。
manual 既不算通过也不算失败——给不出结论时说"给不出结论"，比给一个看着像结论的数诚实。
整体结论的口径是**零 fail**。

**只读文件头。** 一条一小时的 Poly 有几个 GB，整读回来在浏览器里立不住；
头里就有 bext / axml / chna / fmt 与 data 段声明的长度，够核了。

14 条验收清单核的是**计划与内存里的统计**，不是写出去的字节；
**交付自检**（`src/delivery-check.js`）补的就是这一环：把写出去的 Poly 读回来逐条核。
**自检是"工具只判定文件层事实"这条原则的最后一环，它已经补上了。**

## 贯穿全程的几条规矩

不管哪条腿，这几条都不变：

1. **默认关闭。** 凡是会改动音频内容的步骤，都必须用户显式勾选；关着时输出与改动前逐字节相同。
2. **测不出来就不给结果。** 返回 `null` 加一个说得出口的 `reason`，绝不用低置信结果去改音频。
3. **如实报告。** 工具说"没问题"必须是文件层面的事实，不是"我打算这么做"。
4. **本地优先、零外部依赖。** 单文件版要能双击打开就用。
