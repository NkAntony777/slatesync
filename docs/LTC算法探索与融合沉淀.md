# LTC 解码算法探索与融合沉淀总结

> 记录日期：2026-10-06  
> 对应版本：SlateSync v1.5.0  
> 覆盖工作流：`codex` (鲁棒 PLL 解调)、`Mcode` (整数键高性能与漂移补偿)、`docs/ltc-compare` (NDA 前馈定时解调)

---

## 一、背景与核心痛点

SlateSync 是一款面向双系统录音与影视后期声画同步的本地 Web 工具，其核心能力是**从录音导轨音频信号中解码 LTC（SMPTE 线性时间码），逆推文件起始时间戳，并批量合并 Poly WAV 或写回 BWF 元数据**。

在 v1.4.0 之前，原有的解码器面临三类主要挑战：
1. **吞吐量与卡顿瓶颈**：面对长音频（如数十分钟的现场整轨录音），解码器在每个可能的 bit 偏移上使用字符串切片与 `Set.has` 匹配 16 位同步头，单次扫描触发多达上百万次匹配；且在尝试多种备选帧率时，重复对通道音频进行滤波与滑动窗切片，造成严重的无谓开销。
2. **非线性波形与抖动脆弱性**：针对模拟话筒拾音漏音、设备限幅削波、电平波动或变速（vari-speed）时，简单的硬边沿过零判定容易产生伪边沿或丢失边沿，导致帧同步串中断。
3. **极低信噪比下的误锁风险（P0 红线）**：影视后期对于时间码写回有着极端严格的容错要求——**宁可识别不出，绝不可写错 1 帧**。在对白漏音、机位机械噪声与白噪声交织的极端恶劣环境下，如何既扩展低电平/抗噪容忍度，又守住绝对零误锁？

为此，我们并行展开了三个方向的深入探索，并在本地进行了彻底的工程融合。

### 1. `codex` 工作流：鲁棒双相标记 PLL 边沿解调
- **设计思路**：
  将 LTC 编码视为状态机转移过程。在存在失真、相移或干扰时，单个半位间隔会被拉长或压缩。`codex` 提出了对数时序代价模型：
  $$\text{cost}(v, \tau) = |\ln(v / \tau)| + \max(0, |v/\tau - 1| - 0.075) \times 1.8$$
  在边沿到达时，同时生成 3 种候选分支：
  1. 解释为 `bit 0`（跨越 1 个大间隔，消耗 1 个边沿）；
  2. 解释为 `bit 1`（跨越 2 个小间隔，消耗 2 个边沿）；
  3. 解释为受到高频毛刺干扰的 `bit 0`（合并两个杂散短间隔，消除毛刺）。
  随后引入慢速锁相环（PLL，`half += (bounded - half) * 0.035`），平滑适应轻微的带速波动或采样率偏差。
- **产出沉淀**：模块化独立文件 [`src/ltc-robust.js`](file:///D:/game/den/src/ltc-robust.js)，提供高可维护的 [`decodeLtcEdgesRobust`](file:///D:/game/den/src/ltc-robust.js#L4) 接口。

### 2. `Mcode` 工作流：整数键高并发与长音频晶振温漂补偿
- **设计思路**：
  - **滚动 16-bit 整数键与锚定展开**：
    由于 80 位 LTC 帧末尾的 16 位同步头在正向与反向播放时具有固定位模式（`0011111111111101` 与 `1011111111111100`），将其预先哈希为对反转封闭的 16 位整数集合（`0x3FFD`、`0xBFFC` 等）。在位流解码完成后，使用 `Uint16Array` 一次遍历构建位移键，仅在命中同步字的索引处（`syncAnchoredStarts`）才发起 80-bit 候选帧展开。此举直接抹去了原先 72% 的性能开销（消除了每 60s 素材上百万次的字符串操作）。
  - **通道切片预计算提升（Hoisting）**：
    将滤波、直流通带、变体调理与窗口滑动计算提取至 [`prepareChannelAnalysis`](file:///D:/game/den/src/ltc-decoder.js#L936)，当扫描器遍历候选帧率（23.976、24、25、29.97、30 等）时，无需重复切片音频。
  - **后锁定时钟漂移自适应统计（Clock Drift Compensation）**：
    针对录音机与时码器之间硬件晶振温漂（数十至数百 ppm），在长文件多窗口扫描过程中建立加权滑动跟踪器，并在推算文件起始时间戳时，根据估算出的 `driftRatio` 自动纠正时码原点。
  - **工程标准化**：
    设立单一事实来源 [`LTC_TUNING`](file:///D:/game/den/src/ltc-signal.js#L9)，构建了涵盖位对齐（`ltc-parity.test.mjs`）、漂移验证（`ltc-drift.test.mjs`）与性能门禁（`ltc-performance.test.mjs`）的完整测试矩阵。

### 3. `docs/ltc-compare` 工作流：无边沿前馈定时解调器
- **设计思路**：
  源自现代数字通信理论（Oerder–Meyr 平方谱线前馈定时、Gardner 定时误差检测、RFID FM0/Miller 最大似然序列检测）。
  - **核心洞见**：任何基于施密特触发器或过零过阈值的“硬边沿”检测器，在宽带白噪声（SNR < 0 dB）下都会产生海量伪跳变，直接破坏状态机。
  - **算法流程**：
    1. 24-tap 线性相位 FIR 带通预滤波（抑制带外语音与工频底噪）；
    2. 1.5 秒分段，在 $\pm 1\%$ 比特率与相位二维网格上搜索使**半比特积分能量最大化**的最佳采样点（NDA ML 能量准则，无需任何边沿跳变参与）；
    3. 双半比特相位类并行解调，解决 FM0/Biphase 固有的 $\pi$ 相位模糊；
    4. 期望值链式校验（将静态小时/分钟高位跨帧平均，消除单帧软判决误读扩散）；
    5. 段间聚类投票（最大支持簇 $\ge 4$ 且优势比 $\ge 2.0$ 方可放行）。
- **实测战果**：
  在白噪声下达到 -7.3 dB（0.20）的解码极限（比传统边沿解调提升 2.5 dB），在对白干扰下承受 -23.7 dB（0.80），更关键的是在 88 组极端压测中实现 **WRONG=0（绝对零误锁）**。

## 三、融合架构与工程决策

在将上述成果融合至本地主干时，我们进行了严谨的技术选型与安全权衡：

### 1. 为什么主执行链路采用“Mcode 整数键 + codex 鲁棒 PLL”，前馈解调作为模块化基准？
- **浏览器与单文件版延迟需求**：
  主执行链路基于整数键与 PLL 边沿解调，能够在单线程 JavaScript 下提供**百倍至数百倍实时**的解码性能（60s 素材仅需 1.2 秒，900s 素材仅需 1.1 秒，吞吐量高达 786x 实时）。
- **前馈解调器的算力开销**：
  前馈解调需要大抽头 FIR 卷积与二维网格精细积分，60s 素材单线程耗时约 5 秒。因此，将其作为高质量独立模块 [`src/ltc-feedforward.js`](file:///D:/game/den/src/ltc-feedforward.js) 与基准测试套件沉淀，供极恶劣白噪声场景扩展使用。

### 2. 融合中的深水区排坑与防线加固

#### (1) 预处理变体 2-帧浅锁截断软同步问题
- **现象**：在强对白干扰（对白 0.30 vs LTC 0.03）压测中，`interference` 调理变体因鲁棒解调器能力过强，在对白词间间隙拼凑出 2 帧有效锁（`lockedFrames = 2`），但未达到确定性质量；该 2 帧候选作为 `best` 截断了随后的 `if (!best && allowSoftSync)` 降级逻辑，导致能完整锁定 3 帧以上的软同步兜底无法输出。
- **解法**：在 `detectOnChannelData` 中增加守卫：
  ```javascript
  if (variant.conditioned && candidate.lockedFrames < 3) continue;
  ```
  对于经过增益或频段调理的变体，若无 3 帧以上相互印证的连续串，不允许作为确定性阻断结果，从而让软同步逻辑顺利接管。修改后 42 组负样本与压力测试全线通过。

#### (2) 打包压缩（Bundler Minification）变量污染踩坑
- **现象**：使用 `esbuild` 打包单文件 HTML 时，单文件内通过 Blob URL 创建 Web Worker。由于原代码在 Worker 模板字符串中通过 `normalizeLtcAnalysisSignal.toString()` 动态内联函数，`esbuild` 在压缩外层模块时将常量 `LTC_TUNING` 混淆成了短变量名 `Oe`，导致内联进 Worker 字符串的代码残留了 `Oe.analysis`，在独立的 Worker 上下文中抛出 `Oe is not defined`。
- **解法**：在 [`src/ltc-worker.js`](file:///D:/game/den/src/ltc-worker.js) 的 Worker 模板中将 `normalizeLtcAnalysisSignal` 直接声明为自包含函数，彻底脱钩打包工具的外层闭包重命名，并通过 `test/verify-single-file.mjs` 在无头浏览器中建立了每次发布的端到端防线。

## 五、后续维护与演进指南

1. **统一调参入口**：
   调整任何解码门限或评分权重，只修改 [`src/ltc-signal.js`](file:///D:/game/den/src/ltc-signal.js) 中的 `LTC_TUNING`，不要在各控制器内写死硬编码阈值。
2. **Worker 与主线程防分叉**：
   若需修改解码算法逻辑，必须同步在 [`src/ltc-decoder.js`](file:///D:/game/den/src/ltc-decoder.js) 与 [`src/ltc-worker.js`](file:///D:/game/den/src/ltc-worker.js) 中实施，并通过 `npm test:all` 确保 `ltc-parity.test.mjs` 通过。
3. **零误锁防线不可妥协**：
   任何针对低电平或极端噪音的新算法分支，必须通过 `test/ltc-low-level.test.mjs` 中的对白/噪声负样本测试与 `docs/ltc-compare` 的错锁回归，决不能为提高检出率而放宽输出闸门。
