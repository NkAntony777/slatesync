## 2. 修法（照玄学起盘 CLI 的 `docs/034_测试临时目录泄漏修复.md` 同一套来，不另发明）

| # | 底线（缺一不可） | 落点 |
| --- | --- | --- |
| ① | **测试结束必删**（正常结束 / 断言失败 / 异常抛出 / 进程提前退出都要删） | `test/tmp-helper.mjs` 四道钩子 |
| ② | **临时工作目录不落 C 盘系统 TEMP** | 项目内 `<repo>/.tmp/`（D 盘） |
| ③ | **进程启动时清扫超 N 小时（默认 6h）旧残留 + append-only 台账** | `test/tmp-store.mjs::sweepStaleTempDirs()` |

### 2.1 ① 四道清理钩子（缺一条就漏一条路径）

| 钩子 | 覆盖的退出路径 | 实测结果 |
| --- | --- | --- |
| `afterEach`（用例级） | 正常结束、**断言失败**、**异常抛出** | ✅ 探针：故意断言失败 → 目录已删 |
| `after`（文件级） | 整个测试文件跑完（含文件级共享夹具） | ✅ |
| `process.on('exit')` | 未捕获异常、`process.exit()`、正常退出 | ✅ 探针：`process.exit(3)` → 目录已删 |
| `SIGINT` / `SIGTERM` / `SIGHUP` | Ctrl+C、任务被 kill、窗口关闭 | ✅ 探针：三个信号退出码 130 / 143 / 129（= 处理器真的跑了），目录已删 |

- **登记在册**：每个临时目录/文件进 `live` 集合；删除失败（Windows EPERM/EBUSY）**不吞**，留在册上下一轮重试（`fs.rmSync` 带 `maxRetries:5`、`retryDelay:100`）。
- **作用域**：`scope:"test"` 用例级夹具由 afterEach 删；`scope:"file"` 文件级共享夹具（conform 三件套的 `root`）由 after 删——afterEach 不动，否则第二个用例就找不到夹具了。

### 2.2 ② 落到项目内 `.tmp/`（D 盘）——**根本修法**

即使清理失败也不会撑爆 C 盘。目录前缀保持原样（`slatesync-backup-` 等）⇒ 计数、清扫、判废口径与历史一致，同一把尺子量「跑前 / 跑后 / 差值」。

### 2.3 ③ 启动清扫 + 台账

- `sweepStaleTempDirs()` 在**进程启动时**（helper 被 import 即执行）删掉超过 **6 小时**（`SLATESYNC_TMP_SWEEP_HOURS` 可调）的同类旧目录。
- 每删一个目录记一行进 `.tmp/sweep-ledger.jsonl`（**append-only**），最近一次摘要写 `.tmp/sweep-last.json` ⇒ 可与并行清理任务对账。
- **历史 C 盘那批默认不扫**：并发清理任务正在删同一批目录，抢着删会对不上账。需要扫时显式开 `SLATESYNC_SWEEP_LEGACY_TEMP=1`，或单跑 `node test/tmp-sweep.mjs --legacy`（带台账）。

### 5.4 Windows 上的一个实情（必须说清）

`process.kill(pid, "SIGINT")` 在 Windows 上是**无条件终止**（TerminateProcess，等价 SIGKILL），任何 JS 处理器都跑不了——这不是本仓代码的问题，是平台行为。真实 Ctrl+C 走 console control event，Node 会把它派发成 `process.on('SIGINT')`，§5.2 的探针走的就是这条路径。
**不可捕获的强杀（如 kill -9）留下的残留由启动清扫（6h）兜底**——这正是底线③存在的理由。
