# LTC 识别强化：开源方案调研与实测结论

> 调研日期：2026-10-05。本文件记录**可复现的实测结果**，不是厂商认证，也不等于真实摄影机素材的验收。
> 全部数据来自本机合成信号（LTC 波形 + 可控干扰），采样率 48 kHz / 25 fps / PCM16 / 6 秒。
> 基线提交：`src/ltc-decoder.js`、`src/ltc-worker.js`（两侧逻辑需保持一致）。

## 结论先行

1. **开源界没有"更先进的 LTC 识别算法"可直接搬用。** 二十年来事实标准是 `libltc`，其核心是**逐采样自适应阈值 + 连续时钟跟踪**，不是更复杂的模型。神经网络方向的 LTC 解码没有可用的开源实现，本轮检索没有找到任何严肃成果。
2. **本项目识别"弱"的主因不是解调器不够聪明，而是三处结构问题**：解码前的硬门控、软同步路径的验收太松、以及只在信号很干净时才用到的匹配滤波判决被降级成了兜底。
3. **最紧急的问题不是"读不出"，而是"读错且看不出来"。** 兜底模式（`allowSoftSync`）在对白干扰下 **65.8% 的锁定是错的**，误差最大到 809,909 帧（约 33 小时），而 `quality` 仍显示「低」、`confidence` 0.64–0.73，与真实的低质量锁定无法区分。
4. 按通信理论重做解调器（带通 + 半比特栅格锁相环 + 匹配滤波软判决 + 语法校验）后，**对白干扰下的识别门限提升约 19 dB，且全程零错锁**；白噪声场景没有改善，原因见第 4 节。
5. **P0 已实施（2026-10-05）：错锁 25 → 0**，代价是强对白干扰下兜底模式不再出结果。详见第 6 节；后续 P1–P4 未开工。

## 1. 开源方案盘点

| 项目 | 许可 | 核心机制 | 对本项目的价值 |
|---|---|---|---|
| [x42/libltc](https://github.com/x42/libltc) | LGPL-3.0 | 逐采样 min/max 衰减跟踪（等效 AGC）→ 双阈值施密特触发 → 半比特计数判定 0/1 → `period = (period*3+cnt)/4` 连续时钟跟踪 → 16 位同步字移位寄存器精确匹配 → 80 位滑窗 → 静默 >4 个周期则重置 | **最值得借鉴**。逐采样自适应阈值正好治本项目"阈值按窗口全局 min/max 一次算定、遇漂移即失效"的问题；连续时钟跟踪能容忍变速 |
| libltc 输出的 `biphase_tics[80]` | — | 逐位实测半比特周期 | 比现在的 `qualityFor` 启发式合成更可信的抖动/质量指标，可直接用于"是否允许自动写回"的门控 |
| [FrankBoesing/LinearTimecode-Decoder](https://github.com/FrankBoesing/LinearTimecode-Decoder) | MIT | Teensy 端边沿计数 + 帧率自动判定 + LOCK/FREE 状态 | 帧率自动判定思路可参考；嵌入式假设，算法层面无超越 |
| [lalondesteve/goltclib](https://github.com/lalondesteve/goltclib) | 见仓库 | 纯 Go 实时解码 | 无算法创新 |
| [jthwho/libvtc](https://github.com/jthwho/libvtc) | 见仓库 | LTC 编解码 + 时码数学 | 无算法创新 |
| [bitfocus/libltc-wrapper](https://github.com/bitfocus/libltc-wrapper) | MIT（封装 LGPL 二进制） | Node 原生绑定 | **不适用**：本项目要单文件 HTML + Blob Worker，不接受原生模块/WASM 依赖 |

**许可注意**：本项目是 MIT。`libltc` 是 LGPL-3.0，**不能把它的 C 代码复制进本项目**（静态链接/内嵌即触发 LGPL）。可以按其公开描述**重新实现算法思路**——算法本身不受版权保护，表达受保护。上表所有借鉴点都属于"思路"层面。

**关于机器学习**：LTC 是 80 位自同步码，语法高度受限、每帧都自带同步字。用神经网络去解，在信噪比和工程复杂度上都不划算，且没有可复用的开源实现或公开基准。本轮检索未找到严肃成果，不建议投入。

## 2. 现有实现结构（已通读）

`src/ltc-decoder.js` 的链路：

```
readChannel            120 Hz 一阶高通 → 分析增益归一化
  ↓
quickRejectChannel     电平门（peak<0.035 / p2p<0.07）→ 迟滞比较器数边沿
                       → 周期性门（≥800 边沿、≥72% 落在合理半比特区间）
                       → 判 aperiodic / few-ltc-edges 就整条声道跳过  ← 门控在这里
  ↓
channelVariants        raw / balanced(tanh 整形) / interference 三套
  ↓
findEdges              施密特阈值 + 线性插值出边沿
  ↓
decodeBits             按"边沿间隔 ÷ 半比特"分类：2 段=1 bit，1 段=0 bit
                       漏一个跳变就整帧错位；EMA 追踪半比特长度
  ↓
chooseCandidate        精确同步字（0 位错）+ BCD 范围校验 + ≥2 帧连续 +1
  ↓
decodeSoftGrid         固定栅格 + 眼中心匹配滤波 + 软同步字（容 2 位错）
  + softParseFrame     软 BCD（容 5 位错）                ← 只在兜底模式启用
```

一个正面结论：软路径用的判决量 `|x1−x2| > |x1+x2|` **是正确的最优线性判决**（双相码 1 bit 两个半比特反相、0 bit 同相）。原型复现时我一开始用 `x2−x1` 立刻全盘失败，换成乘积符号才对——项目这一处的数学是对的，不需要重写，需要的是把它从"兜底"提到"主路径"。

## 3. 实测：当前实现的识别边界

`allowSoftSync = false`（产品默认路径），LTC 幅度 0.05：

| 场景 | 结果 |
|---|---|
| 干净 0.5 | ✅ 高 |
| −30 dBFS 低电平 0.03 | ✅ 高 |
| 50 Hz 交流声堆叠 0.15 | ✅ 高 |
| 限带 400–3200 Hz | ✅ 高 |
| 软削波 | ✅ 高 |
| 时钟 +0.4%（变速） | ✅ 中，误差 0.1 帧 |
| 1 秒信号丢失 | ✅ 高，误差 0 帧 |
| 白噪声 0.15（SNR −4.8 dB） | ✅ |
| **白噪声 0.20（SNR −7.3 dB）** | ❌ 门控判 `aperiodic`，整条跳过 |
| **对白干扰 0.30（SNR −15.2 dB）** | ❌ 门控判 `aperiodic`，整条跳过 |
| **对白干扰 0.50（SNR −19.7 dB）** | ❌ 无锁定 |

默认路径**零错锁**，这一点是安全的；代价是门限偏保守。

## 4. 实测：三个结构性问题

### 4.1 兜底模式会静默返回错值（最高优先级）

兜底模式（`allowSoftSync: true`）下，8 个随机种子 × 6 个对白干扰电平，共 48 次：

```
ok=13   WRONG=25   no-lock=10     错锁率 65.8%
```

错读样本（真实时码均为 `01:00:00:00` 起始）：

| 读到的时码 | 误差（帧） | quality | confidence |
|---|---|---|---|
| `01:00:01:10` | −10 | 低 | 0.73 |
| `01:00:04:09` | −10 | 低 | 0.68 |
| `09:20:05:13` | +750,100 | 低 | 0.72 |
| `10:00:01:10` | +809,909 | 低 | 0.64 |
| `00:18:01:03` | −63,004 | 低 | 0.66 |

**机制**：`softSyncMatch` 允许同步字错 2 位、`softParseFrame` 允许 5 位错、`softFrameAt` 只要求 BCD 落在合法区间。80 位里容 7 位错后，随机模式撞上"合法 BCD + 连续 3 帧 +1"的概率足够高，于是稳定的假锁定吸引子出现了——注意上表里反复出现同样几个假时码，这是系统性而非偶发。

**风险**：`ltc-controller.js:350` 提示"低质量结果请人工确认"，但随后仍会把这个具体数字写进 WAV 的 TimeReference。人工确认面对一个"低/0.7"的自洽数字很难发现异常，而正确做法是**不给出数字**。

> 缓解：兜底模式是显式 opt-in（`allowSoftSync` 默认 false），不污染默认路径。属于需要修，但不是默认路径上的数据损坏。

### 4.2 预处理没有针对 LTC 频段

LTC 是双相标记码（biphase mark），全 0 载波 1.2 kHz、全 1 载波 2.4 kHz（30 fps），即信号只占据 `[f_bit/2, f_bit]`，`f_bit = 80 × fps`（25 fps → 1–2 kHz）。

现有 `highPass(120 Hz)` + `lowPass(9000 Hz)` 把 **0–9 kHz 全部放进来**，对白、节目声、交流声谐波全部进入比较器。实测把 700–2600 Hz 带通加在门控**之前**（否则门控先拒）后，对白干扰下多救回一个 −32 dB 场景，但白噪声场景无改善——因为瓶颈在门控与解调器，不在滤波器。

### 4.3 边沿间隔分类式位同步在宽带噪声下退化

`decodeBits` 靠"间隔 ÷ 半比特"落在哪个区间来判定 0/1 bit。噪声制造的伪跳变会污染间隔，漏掉一个真跳变就整帧错位且无法自愈。libltc 的做法是**不让判决参与时钟**：始终用连续时钟推进网格，判决只发生在眼中心。

## 5. 原型验证：按通信理论重做解调器

在不改仓库代码的前提下，用临时原型替换解调器做了对照（临时文件见第 8 节）：

```
带通(700–2600 Hz, 193/385 taps, 线性相位 FIR)
  → 施密特跳变检测（仅用于给锁相环提供相位/频率牵引）
  → 半比特栅格二阶锁相环（Bn=0.006, ζ=0.707）
  → 眼中心匹配滤波：x1 = 半格1均值, x2 = 半格2均值
  → 判决 sign(|x1−x2| − |x1+x2|) 得到软 LLR
  → 精确同步字 + BCD + 连续 3 帧 +1
```

| 场景 | 现有实现 | 原型（700–2600, 385 taps） |
|---|---|---|
| 白噪声 0.10 | ✅ | ✅ |
| 白噪声 0.15（−4.8 dB） | ✅ | ✅ |
| 白噪声 0.20（−7.3 dB） | ❌ | ❌ |
| 对白 0.30（−15.2 dB） | ❌ | ✅ |
| 对白 0.50（−19.7 dB） | ❌（兜底模式下错锁） | ✅ |
| **对白 0.80（−23.7 dB）** | ❌ | ✅ |
| **对白 1.20（−32.8 dB）** | ❌ | ✅ |
| 纯白噪声 0.30 / 0.80 | 正确拒绝 | 正确拒绝 |
| 纯对白 0.30 | 正确拒绝 | 正确拒绝 |
| 错锁次数 | 兜底模式 65.8% | **0** |

**对白干扰识别门限提升约 19 dB，且全程零错锁。** 带通参数扫描结论：700–2600 Hz（= `0.7·f_bit/2` ~ `1.3·f_bit`）明显优于任何更宽的频带；97 taps 对白到 0.80，193 taps 白噪声到 0.15，385 taps 对白到 1.20。

**白噪声为什么不改善**：锁相环仍然以跳变为牵引源，宽噪声制造的伪跳变照样进入环路。彻底解决需要**前馈定时**（用自相关/频谱估计码元速率，噪声伪跳变完全不参与定时），即把现有 `softPhaseCandidates` + `decodeSoftGrid` 的开环思路做成主路径并配合语法约束判决。这是下一步的收益点，本轮未做。

## 6. 已实施：P0 收紧验收（2026-10-05）

P0 的目标是止损——不提升识别率，只保证"读不出"时不会变成"读错"。阈值全部来自实测，不是拍的。

### 6.1 先否掉一条方案：边沿路径交叉校验不可用

原计划"软路径结果必须被边沿路径交叉验证"。**实测否决**：软路径只在 `if (!best && allowSoftSync)` 时才进入，也就是说边沿路径已经**没有结果**才会跑软路径。对 13 个正确软锁做边沿侧佐证测量，**命中 0/13**。把它当验收门会用 100% 拒绝率把软路径整个废掉。

同时测了其他候选特征，**没有一个能区分对错**：

| 特征 | 正确锁 | 错锁 | 结论 |
|---|---|---|---|
| `softSyncSupport`（相位簇） | 5–16 | 2–14 | 重叠 |
| `softSyncMargin` | 0.682–0.823 | 0.693–0.750 | 重叠 |
| `softFrameConfidence` | 0.711–0.865 | 0.627–0.820 | 重叠 |
| `softSyncErrors` | 0–2 | 0–2 | 重叠 |
| 80 位偶校验 | 8/13 有效 | 8/25 有效 | 区分度弱，且测试编码器未置该位 |
| **`lockedFrames`（连续帧数）** | **2–6，5/7 ≥3** | **1–2，无一 ≥3** | **唯一干净的判别器** |

**唯一有效的信号是连续帧数。** 原因也清楚：固定栅格的软路径在累积漂移后无法维持长串，所以长串本身只可能来自真实 LTC；随机模式撞出连续 3 帧时码递增的概率极低。

### 6.2 实际改动

`src/ltc-decoder.js` 与 `src/ltc-worker.js`（两侧镜像同步）：

| 位置 | 改前 | 改后 |
|---|---|---|
| 连续帧要求 | `run.length >= 2` | `run.length >= 3`（`SOFT_MIN_RUN_FRAMES`） |
| 逃生门 | `runFrames < 2 && cluster < 4` 放行 | 移除；要求 `runFrames >= 3` **且** `cluster >= 3` |
| 簇余量门 | 按 run 分档 0.64 / 0.72 | 统一 `0.64`（余量不可区分，不再分档） |
| `qualityFor` | 软路径 `lockedFrames < 4` 判"低" | 软路径 `softConfirmOnly`（`run < 6`）判"低" |
| 软候选标记 | 无 | 新增 `requiresConfirmation: true` |

`src/confirm-flows.js` + `src/time-reference-write-controller.js` + `index.html`：

- 新增 `confirmSoftSyncWrite()` 专属确认弹窗，**逐条列出**要写入的起始时码、源帧、连续帧数。
- 兜底结果**不再混入**通用"确认写入 N 个"弹窗；只要有兜底结果，先走这个专属弹窗。
- `src/ltc-controller.js` 状态栏单独统计并提示兜底结果数量。

### 6.3 效果

| 指标 | 改前 | 改后 |
|---|---|---|
| 48 例压力矩阵错锁 | **25（65.8%）** | **0** |
| 错锁最大误差 | 809,909 帧（≈33 小时） | — |
| 白噪声 0.10（SNR −9 dB）软锁 | ✅ run=6 | ✅ run=6 保留 |
| 白噪声 0.15（SNR −12 dB）软锁 | ✅ run=3 | ✅ run=3 保留 |
| 对白 0.25 / 0.30 / 0.35 软锁 | ✅ run=3 | ✅ run=3 保留 |
| 对白 0.40 软锁 | ✅ run=2 | ❌ 拒绝（该区间 25/25 邻居全错，拒绝是对的） |
| 纯噪声 / 纯对白误接受 | 0 | 0 |

`test/ltc-low-level.test.mjs` 新增两条回归：

- `fallback mode never returns a wrong timecode under interference` — 6 种子 × 7 干扰档压测，断言**错锁数必须为 0**，并断言 `locks > 0` 防止测试退化成空断言。
- `fallback mode still recovers runs that satisfy the strict grammar` — 白噪声与对白两个场景断言召回未被误伤，且 `requiresConfirmation` 已置位。

全量测试 28 项通过；单文件构建后浏览器验证 11/11 通过（含 Blob URL Worker 解码）。

### 6.4 P0 仍未解决

- 兜底模式在**强对白干扰（voice ≥0.40）下已完全不出结果**。这是 P0 的预期代价：那一档本来 100% 是错读。要把召回拿回来只能靠 P2。
- 80 位偶校验校验位**未启用**：项目测试编码器 `test/ltc-encode.mjs` 不置该位，先修编码器让它合规，再作为辅助判据，否则会误杀自己的测试信号。
- 单帧级诊断（"检测到信号但未通过严格校验"）未接入 `channelReports`，目前用户只能看到"没检测到"。

## 7. 后续升级路线

**P1 — 前置换入 LTC 频段带通**（实测对白场景多救一个档位）
- 按候选 fps 计算 `f_bit = 80 × fps`，加线性相位 FIR 带通 `[0.7·f_bit/2, 0.3·f_bit]`；默认 193 taps，385 taps 用于"对白主导"档（实测 385 taps 把对白识别从 0.80 推到 1.20）。
- 必须在 `quickRejectChannel` **之前**应用，否则门控拿到的还是宽带统计量。
- 一阶 IIR 串联会引入相位散射、拉闭眼图，这里要线性相位 FIR；工程上对 4 秒窗（192k 采样）做 193 taps 约 37M 次乘加，单声道可接受，60 秒整扫建议分窗或改用重叠相加。

**P2 — 半比特栅格锁相环 + 匹配滤波软判决升为主路径**（实测对白门限 +19 dB、零错锁）
- 保留现有边沿路径做快速通道；新增锁相环路径做主通道；两者结果送同一个校验器。
- 判决统计量沿用现有的 `|x1−x2| > |x1+x2|`（数学已正确），补上**逐位 LLR** 供软同步字/软 BCD 使用。
- **这是把 P0 牺牲掉的兜底召回拿回来的唯一已验证路径**；做完之后 P0 的严格门可以适度放宽。
- `src/ltc-decoder.js` 与 `src/ltc-worker.js` 必须同步改。

**P3 — 帧率前馈估计 + 逐位抖动质量指标**
- 用带通信号在候选码元速率上的自相关/频谱峰替代"边沿间隔中位数"来定 fps，对宽带噪声稳健得多（现 `estimateHalfBitSamples` 在噪声下本来就不可靠，这正是门控误判的根因之一）。
- 引入 libltc 式的逐位半比特周期数组，替换 `qualityFor` 的启发式合成。

**P4 — 白噪声场景的软判决**
- 锁相环以跳变为牵引源，宽带噪声的伪跳变会进环（这就是第 5 节里白噪声没有改善的原因）。需要**前馈定时**（自相关估码元速率），让噪声伪跳变完全不参与定时，即把 `softPhaseCandidates` + `decodeSoftGrid` 的开环思路做成主路径。

## 8. 未覆盖 / 风险声明

- 全部数据基于**合成信号**。真实录音机（ZOOM H6 等）的 LTC 可能带不同的上升时间、削波、DC 漂移和 codec 预处理，数字会变。
- 只验证了 48 kHz / 25 fps。`23.976` / `29.97df` / `24` / `30` 以及 44.1 / 96 kHz 未纳入本轮对照。
- 变速只测了 +0.4% 恒定偏移，未测连续变速（变声/调速）。
- 多声道隔离未测（本轮全为单声道）。带通可能改变多声道间的相位关系，需确认不会影响 Poly 输出的通道对齐。
- 第 5 节的原型是**独立脚本**，未接入 `src/`；P1–P2 的工程量与对 `ltc-worker.js` 的同步改动尚未评估。
- 第 5 节的"零错锁"是在 14 个受控场景上的观测，**不等于任意素材上不会错锁**。P0 的专属确认弹窗是必要的兜底，不是可选项。
- P0 的压力矩阵是单声道 25 fps 的合成对白，**不代表真实素材上的错锁率**。阈值 `SOFT_MIN_RUN_FRAMES = 3` 是按"随机模式撞出连续 3 帧递增 BCD 的概率极低"这一推理定的，没有在真实素材上标定过。

## 9. 复现方式

基准脚本放在临时目录，未进仓库（它们会 monkey-patch 解码器，形态不适合直接作为回归测试）：

```
%TEMP%\ltc-research\bench-current.mjs      # 现状基线
%TEMP%\ltc-research\bench-integrity.mjs    # 默认路径 vs 兜底模式的错锁率

%TEMP%\ltc-research\bench-pll2.mjs         # 锁相环 + 匹配滤波原型
```

跑法：`cd D:\game\den; node %TEMP%\ltc-research\<脚本名>`。这些脚本从 `file:///D:/game/den/...` 导入仓库源码，仓库如有改动需重跑。

其中"错锁数必须为 0"与"严格语法下召回不丢"两条已经固化进 `test/ltc-low-level.test.mjs`（见 §6.3），随 `npm test` 执行。
